# 19 · 通知延迟与丢失的修复方案

> 面向问题：「系统通知仍有延迟；App 未打开（前台没运行 / 后台被终止）时完全收不到通知」。
> 本文按 **产生 → 传输 → 展示** 三段拆链路，逐点写明根因、改法与影响，最后给出可执行的验证步骤（含延迟测量）。

---

## 一、先看链路：一条提醒要经过几道手

```
T-15min  页面算出提醒时刻 remindTimeOf(todo)
           │
           ├─(A) 前台路径：setInterval / setTimeout 轮询到点
           │      → window.Android.notify() → NotificationManager
           │
           └─(B) 后台路径：scheduleAlarms() → Android.setAlarms(json)
                  → AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, at, PendingIntent)
                     │
           （到点，App 进程可能早已不在）
                     ▼
                  AlarmReceiver.onReceive()
                     → Reminders.notify() → NotificationManager
                     → ??? 下一条谁来排 ???
```

旧实现的问题集中在 **(B) 这条路径的「谁来续排」**，以及几条「静默失败」的权限判断。通知本身的构造、渠道、图标都是对的——所以现象看起来像「通知坏了」，其实是「闹钟没排上」。

---

## 二、逐点审查结果

| 审查点 | 发现 | 后果 |
| --- | --- | --- |
| `Reminders.schedule()` | `MAX_ALARMS = 3`，只取最近 3 条 | 第 4 条起永远不响 |
| `AlarmReceiver.onReceive()` | 只发通知 + 震动，**不重新排下一次** | 3 条响完后彻底静默 |
| 提醒计划存放位置 | 只存在 WebView 的 IndexedDB（`S.records`），原生无副本 | 进程被杀 / 重启后无从重排 |
| `AndroidManifest.xml` | 无 `RECEIVE_BOOT_COMPLETED`，无开机接收器 | 重启手机 → 所有闹钟被系统清空且永不恢复 |
| 精确闹钟 | 声明了 `SCHEDULE_EXACT_ALARM`，但从不调 `canScheduleExactAlarms()` 也不引导授权 | Doze 下退化为 `setAndAllowWhileIdle`，最晚拖十几分钟 |
| 通知权限 | `onRequestPermissionsResult` 只处理 `REQ_CAMERA`，`REQ_NOTIFY` 结果被丢弃 | Android 13+ 首次启动被拒后，一条都弹不出来且无任何提示 |
| 前台轮询 | `setInterval(sweep, 30s)` + `OVERDUE_GRACE = 15min` | 到点最多晚 30 秒；关闭超过 15 分钟直接跳过 |
| 关闭开关 | `S.meta.notifyTodo === '0'` 只让 `checkTodos` 提前返回，已排的原生闹钟不撤 | 关掉提醒后照样响 |
| 前台 / 原生去重 | 原生发通知不写 `notifiedMap` | 后台响过，再打开 App 又弹一次 |
| `KeepAliveService` | `START_STICKY` 前台服务，但默认关闭（`keepAlive !== '1'`） | 只是加分项，不能当兜底 |

---

## 三、根因归纳

1. **闹钟是一次性资源，没人续排。** `AlarmManager` 的条目响过即销毁；旧代码把「排闹钟」当成页面的一次性动作，于是 App 不打开 = 没有新闹钟 = 不响。这是「完全收不到」的**主因**。
2. **计划没有原生副本。** 页面不可用时（进程被杀、重启），原生手里没有任何「还欠用户几条提醒」的信息。
3. **重启是硬清零。** 系统重启会清空所有 App 的闹钟，必须有 `BOOT_COMPLETED` 接收器重排，否则此后永久失效。
4. **权限是静默降级。** 精确闹钟与通知权限都可能为否，旧实现两种情况下都"正常工作"——只是不响。
5. **前台靠轮询、宽限太短。** 30 秒粒度 + 15 分钟宽限，既慢又容易漏。

---

## 四、改动点：做了什么、起什么作用、有什么影响

### 改动 1 · 提醒计划下沉到原生并持久化

**改法**：`Reminders` 用 `SharedPreferences("xhub_reminders")` 存整份计划（`plan`，上限 60 条），字段 `{at, title, body, tag}`；`tag` 是去重键（`todo-<id>` / `pomo` / `selftest`）。从计划里取最近 8 条挂进 `AlarmManager`（槽位 0..7）。计划文本未变时直接返回，不重排。

**作用**：App 进程随时可以没有，但「还欠哪些提醒」始终在磁盘上。

**影响**：
- 内存/存储开销可忽略（60 条 × 约 100 字节）。
- 编辑待办时 `onChange` 会反复触发 `setAlarms`，靠"计划未变则跳过"避免每次都全撤全排——否则会在到点那一瞬把正在派发的闹钟撤掉。
- 上限从 3 提到 8（系统内并发闹钟上限是 500/App，8 条远未触顶）；8 条之外的靠"到点续排"补上。

### 改动 2 · 到点自动续排（本次核心）

**改法**：`AlarmReceiver.onReceive()` 先 `goAsync()` 并持有 10 秒 `PARTIAL_WAKE_LOCK`，然后依次：发通知 → 震动 → 记事件 → `Reminders.onFired()` 从计划里摘掉这条 → **把剩下的重排进系统** → `finish()`。

**作用**：补排发生在广播里，不经过 WebView。App 没运行、进程被回收、界面从没打开过，都能一条接一条地响下去。

**影响**：
- 每条提醒多一次 SharedPreferences 读写（同步 `commit()`，毫秒级），必须在广播的 10 秒窗口内完成，故用 WakeLock 保底。
- 若用户在两条提醒之间改了计划，页面下发的计划覆盖原生计划，不会重复。

### 改动 3 · 开机 / 更新 / 改时间后重排

**改法**：新增 `RestartReceiver`，监听 `BOOT_COMPLETED`、`QUICKBOOT_POWERON`（国产 ROM 私有 action）、`MY_PACKAGE_REPLACED`、`TIME_SET`、`TIMEZONE_CHANGED` → `Reminders.rearmAfterRestart()`：丢弃未来项以外的过期项，12 小时内错过的记成 `late` 事件，然后重排。

**作用**：解决"重启一次手机，从此收不到提醒"。

**影响**：新增 `RECEIVE_BOOT_COMPLETED`、`WAKE_LOCK` 两个普通权限（安装时授予，无弹窗）。关机超 12 小时的提醒不再补发，避免一次性涌出大量过期提醒。

### 改动 4 · 权限从「声明」变成「可查、可引导、有反馈」

**改法**：
- `Reminders.state()` 返回 `{exact, notify, channel, plan, armed, next, lastAt, lastFire, lastDelay}`。
- 设置页新增 **通知自检**：四行状态灯 + 异常项的「去开启 / 去允许 / 去设置」。
- 「去开启」先走 `requestNotifyPermission()`（运行时申请），失败再 `openNotificationSettings()`。
- 精确闹钟走 `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM`；拿不到时仍退化为近似闹钟而不是不响。
- `onRequestPermissionsResult` 处理 `REQ_NOTIFY`：被拒时 Toast 明说后果，并 `emit('notifyperm')` 通知页面。

**作用**：把"为什么收不到"从用户猜变成页面直读。

**影响**：Android 13+ 首次启动仍会弹一次权限框（时机未变），但被拒后不再静默。

### 改动 5 · 前后台时序对齐

**改法**：
- 新增 `lib/plan.js`，纯函数承接：`planItems()`（下发哪些）、`dueNow()`（此刻该响哪些）、`nextDueAt()`（下次几点）、`readAlarmEvents()`（日志对账）。
- `alerts.js` 按 `nextDueAt()` 精确 `setTimeout`（`next - now + 120ms`，上限 60 秒兜底），30 秒轮询保留为兜底。
- `visibilitychange`：切走前 `scheduleAlarms()` 把计划钉进系统；回来后 `reconcile()` → `sweep()` → `scheduleAlarms()`。
- `notifyTodo === '0'` 时 `cancelAlarms()`。

**作用**：前台延迟从「最多 30 秒」降到「百毫秒级」；关掉开关真的关掉。

**影响**：多一个 `setTimeout`（可忽略）；`remindTimeOf` 逻辑未变，历史数据无需迁移。

### 改动 6 · 去重与补发

**改法**：原生每次响过往 `event` 表记 `{tag, at, ts, late}`（上限 80 条）。页面启动 / 回前台时 `takeAlarmEvents()` 取走并清空：
- `late=false` → 写 `notifiedMap`，页面不再弹第二次；
- `late=true` → 进 `missed` 集合，允许突破 15 分钟宽限、在 12 小时内补发一次，文案标「补发 ·」。

**作用**：修掉"后台响过、开 App 又弹一次"，同时保住"关机期间错过的还能看到"。

**影响**：`notifiedMap` 增加原生写入来源，仍按 `id@时刻` 去重，语义不变。

## 五、时序对比

```
旧：  09:00 提醒1 ✅   09:30 提醒2 ✅   10:00 提醒3 ✅   10:30 提醒4 ❌（从未排上）
      重启手机 → 全部 ❌        后台被清理 → 全部 ❌        通知权限被拒 → 全部静默 ❌

新：  页面下发 [1..N] → 原生存盘 + 挂前 8 条
      09:00 提醒1 ✅ → 广播里摘掉1、补排9
      09:30 提醒2 ✅ → 摘2、补排10
      …
      重启手机 → RestartReceiver 重排 ✅
      后台被杀 → 闹钟仍在系统里 ✅
      exact 被关 → 自检页红点 + 一键跳设置，仍会响（可能晚几分钟）
```

## 六、验证方式

### 6.1 自动化（开发侧）

```bash
node --test android/tests/*.test.mjs     # 153 项：含新增 alerts-plan 25 项
node _tools/notify-check.mjs             # 26 项：全量下发 / 对账 / 补发 / 自检 / 撤闹钟
node _tools/home-check.mjs               # 100 项回归
node _tools/tab-gesture-check.mjs        # 22 项回归
```

`notify-check.mjs` 在真实页面里跑，只把原生桥替换成记录器，断言四件事：
1. 6 条待办 → `setAlarms` 收到 5 条（未来项全量，不再截断到 3）；
2. 已到点那条不进计划、原生已响过的写进 `notifiedMap`、页面不再重复弹；
3. `late=true` 的（2 小时前）会补发且标注「补发 ·」；
4. 关开关 → `cancelAlarms()` 被调用且计划清空。

### 6.2 真机：延迟测量

1. 设置 → 提醒 → **通知自检**，确认前三行都是绿点（否的话先点右侧按钮修）。
2. 点「10 秒后测试提醒」，**立刻锁屏**。
3. 到点应弹通知并震动。回到设置页，「上次提醒」一行会显示 `今天 HH:MM · 延迟 晚 N 毫秒`。
   - 这个数是原生记录的 `now - at`，即闹钟触发时刻与计划时刻之差，就是端到端延迟。
   - 判定：`exact = 已允许` 时应 < 1 秒；若只有几十秒到十几分钟，说明精确闹钟权限没给或系统在省电。
4. 对照实验：把「精确闹钟」关掉（系统设置里撤销）再测一次，会看到延迟显著变大——这就是修复前所有用户的处境。

### 6.3 真机：App 未打开

| 场景 | 步骤 | 预期 |
| --- | --- | --- |
| 前台关闭 | 建 5 条待办，提醒设在 2/3/5/6/8 分钟后 → 按 Home 或从多任务划掉 | 5 条逐个弹出（旧版只响前 3 条） |
| 进程被杀 | 同上，用 `adb shell am kill com.zhou.todolink` | 同上 |
| 重启手机 | 建 1 条 10 分钟后的提醒 → 重启（**不要**打开 App） | 到点仍弹出 |
| 不重复 | 让一条在 App 关闭时响过 → 再打开 App | 不再弹第二次、通知栏不出现第二条 |
| 关开关 | 关掉「待办临期提醒」 | 之后不再有通知；重新打开后恢复 |
| 未授权 | 系统设置里关掉本 App 通知 | 自检第一行变红，点「去开启」能回到授权入口 |

### 6.4 判定标准

- 延迟：`exact` 允许时 < 1 秒；不允许时允许数十秒，但**必须仍会响**。
- 覆盖：连续 5 条以上提醒全部触发，不因数量被截断。
- 持久：重启、杀进程、覆盖安装后，未到点的提醒仍会响。
- 不重复：同一条提醒在任意路径下只出现一次。

## 七、遗留边界

1. 计划来自页面：App 长期不打开时，电脑端新改的提醒要等下次打开 App 才重排（沿用原有同步模型）。
2. 同一分钟内多条提醒在 Doze 下受系统"每 9 分钟一次"的配额限制，会顺延到下一个唤醒窗口——不是丢，是晚。
3. 国产 ROM 的"自启动 / 后台运行"是厂商私有策略，App 无法自证；自检页已给出提示文案。
4. 关机超过 12 小时的提醒按设计丢弃。
