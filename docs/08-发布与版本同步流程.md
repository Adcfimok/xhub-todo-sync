# 发布与版本同步流程

> 规则一句话：**产物进仓库 = 版本被发布**。把新的 zip / apk 提交并推到 `main`，Release 自动建好；
> 标签永远钉在「包含该产物的那个提交」上，所以仓库代码与 Release 不会错位。

## 1. 两条独立版本线

| 产物 | 类型标识 | 版本号来源 | 标签格式 |
| --- | --- | --- | --- |
| 扩展分发包 `dist/com.zhou.todo-relay-<x.y.z>.zip` | `xhub-extension` | `dist/.../manifest.json` 的 `version` | `xhub-ext-v<x.y.z>` |
| 安卓安装包 `android/todo-link-<x.y.z>.apk` | `android-apk` | `AndroidManifest.xml` 的 `versionName` | `android-v<x.y.z>` |

两条线互不牵连：扩展 2.1.0 可以配 APK 2.8.0。APK 另需 `versionCode` 单调递增，
否则覆盖安装会被系统拒绝（当前 2.8.0 为 12）。

## 2. 发一个新版本，只需三步

1. **放产物**：按上面的命名规则放到 `dist/` 或 `android/`。
   名字不合规的不会被识别（`upload.test.mjs` 里有命名用例，可对照）。
2. **写版本说明**：`_tools/release-upload/notes/<kind>-<version>.md`，写法见同目录 `README.md`。
   缺这个文件不会挡住发布，但 Release 正文会退化成「只含产物事实」的兜底版本，并在开头注明缺失。
3. **提交并推送**：

   ```bash
   git add dist android _tools/release-upload/notes
   git commit -m "release: 安卓端 2.9.0"
   git push origin main
   ```

   也可以让脚本代劳登记与推送：

   ```bash
   node _tools/release-upload/sync.mjs            # 体检：哪些产物还没进清单
   node _tools/release-upload/sync.mjs --push     # 登记 + 提交 + 推送
   ```

## 3. 推送之后自动发生什么

`.github/workflows/publish-releases.yml` 在 `dist/*.zip`、`android/*.apk` 或上传器代码变更时触发：

1. 跑单测（顺序、去重、幂等、失败即停、标签与正文）；
2. `upload.mjs --discover` 扫描实际产物，与 `versions.json` 合并去重；
3. 逐条解析：标签（按类型模板）、Release 标题、说明正文、**产物所属提交**（`git log -1 -- <file>`）；
4. 先建标签 ref（指向该提交），再建 Release，再传资产；
5. `verify.mjs` 回查四条事实：Release 存在、资产同名、大小与 SHA-256 一致、标签指向产物提交；
6. 结果写入 `release-results/latest.json` 与 `release-results/verify-latest.json`，并回写仓库；
7. 校验不通过 → 本次运行失败（红叉），不会静默留一个「看起来发了」的版本。

`.github/workflows/verify-releases.yml` 每天 09:00 再巡检一次，防止「当时发成功、后来被改坏」。

## 4. 本地能做什么、不能做什么

| 命令 | 作用 | 需要令牌 |
| --- | --- | --- |
| `node _tools/release-upload/upload.mjs --dry-run` | 打印发布计划（标签、标题、提交、校验和），不写远端 | 否 |
| `node _tools/release-upload/verify.mjs --offline` | 用 `git ls-remote` 比对标签，检查清单/说明/提交是否齐 | 否 |
| `node _tools/release-upload/sync.mjs` | 体检新产物是否已登记 | 否 |
| `node _tools/release-upload/sync.mjs --push` | 登记 + 提交 + 推送，触发云端发布 | 否（走 SSH） |
| `node _tools/release-upload/upload.mjs` | 真正建 Release 并上传 | 是 |
| `node _tools/release-upload/verify.mjs` | 走 API 全量核对资产与标签 | 是 |

本机不保存长期令牌，所以「真正建 Release」这一步交给 GitHub Actions 用平台内置令牌完成——
令牌不落地，标签也由同一次运行创建，天然对齐。

## 5. 补救与重发

- **发布失败 / 想重跑**：Actions → 「发布版本到 Releases」→ Run workflow。上传器是幂等的，
  已存在的同名资产会 `skipped`，只补缺失的部分。
- **资产传错了**：换掉文件、把 `version` 提一位（例如 2.8.1），重新推送。
  **不要**在原版本号上覆盖同名资产——已下载的人拿到的是旧文件，校验和会对不上。
- **忘了写说明**：补 notes 文件后重新推送即可（`_tools/release-upload/**` 也在触发路径里），
  但正文只在建 Release 时写入；已建的那条需在网页上编辑，或删掉 Release 重跑（标签会复用）。
- **标签指错了提交**：不会自动修。确认 `git log -1 -- <file>` 与标签指向不一致时，
  手工删除标签与 Release 后重跑工作流。

## 6. 一致性口径

判定「一致」要同时满足：

1. 产物文件在仓库里，且该提交在 `origin/main` 上；
2. 存在对应标签，标签指向的提交 == 最后修改该产物的提交；
3. Release 里有同名资产，大小与 SHA-256 与仓库里的文件一致。

三条都由 `verify.mjs` 检查，任一不满足即 `drift`。

## 7. 遗留说明

`version-archive` 是早期「把历史产物归档到一个 Release」流程留下的标签与发布，
其中的资产与 v2.1.0 / 2.7.0 / 2.8.0 三条独立 Release 重复。
保留是为了不打断可能存在的旧下载链接；**新版本一律走一版一 Release**，不再写入该归档。
