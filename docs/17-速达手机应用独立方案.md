# 17 · 速达：PC 端程序与手机端应用彻底分离（3.5.0）

> 本文说明本次改动的具体方案、数据边界与涉及的关键代码模块，便于逐项核对。

## 1. 改造前的问题

速达原来只有**一个** `resources` 集合（PROTO 2 同步集合），里面按 `kind` 混着三类：
`web`（网页）、`file`（文件）、`app`（程序）。但 `app/file` 其实是 **PC 上的程序**：
扩展侧 `hub.json` 里就是 `{"kind":"app","target":"code.exe","icon":"C:\\...\\icons\\xxx.png"}`。
手机端点开只能弹「文件与程序只能在电脑上打开」——这就是要取消的「原有 PC 端程序方案」：
把 PC 程序混进手机速达的同一套数据、筛选和新建逻辑里，还试图在手机上管理/打开它们。

## 2. 改造后的两个完全独立的个体

| | 个体一：手机应用 | 个体二：电脑同步 |
| --- | --- | --- |
| 数据存储 | `S.meta.phoneApps`（IndexedDB `meta` store） | `records` 里的 `resources` 集合 |
| 是否参与同步 | **否**。`syncNow()` 只推 `S.records` 的脏记录，meta 不在 PROTO 2 载荷内 | 是，仍与 PC 端 PROTO 2 同步 |
| 数据来源 | 本机 `PackageManager` 的已安装应用 | PC 端同步下来的 `web/file/app` 记录 |
| 展示 | 小图标网格（自动换行） | 原卡片网格 + 筛选条 |
| 功能 | 添加 / 启动 / 移除 | 网页可打开、编辑、删除；`app/file` **只读**、不可打开、不可编辑 |
| 新建 | 只能从本机应用列表挑 | 只能新建「网页入口」，不再提供程序/文件类型 |

**互不影响的保证**：两个分区不共享筛选状态（`zone` / `filter` 分开）、不共享数据、
不互相转换类型；添加/移除手机应用走 `saveMeta()`，它不 `emit()` 也不 `scheduleSoon()`，
所以既不会重绘别的页面，也不会发起一次同步；PC 端同步触发的 `onChange(render)` 只重绘视图，
手机应用仍从 `S.meta.phoneApps` 读，一条不多一条不少。反之 PC 端永远看不到这台手机装了什么。

> 关于「取消 PC 端程序方案」的落点：手机端不再新建 `app/file`、不再提供打开入口、
> 不再把 PC 程序混进「程序」主功能区；历史同步过来的 PC 程序保留在独立分区里**只读展示**并标注「电脑端」，
> 以便用户仍能看到电脑侧有什么，但两边数据与功能已经彻底断开。

## 4. 真实图标是怎么来的（不使用统一占位图）

```
PackageManager.getApplicationIcon(pkg)  → Drawable（含 Android 8+ AdaptiveIconDrawable）
  → 96×96 ARGB_8888 Bitmap + Canvas.draw  → PNG 文件
  → /cacheDir/appicons/<md5(pkg)前8字节>.png
  → AssetServer 的 /__appicon/<hash>.png（同源回环 HTTP）
  → <img src="/__appicon/..."> 由 WebView 加载
```

- 图标文件按包名哈希命名，同一个应用始终是同一张系统图标；不使用任何通用占位图形。
- 用「原生写文件 + 本地 HTTP」而不是把图标 base64 塞进 JS 桥返回值：几百个应用的 base64 会撑到 Binder 上限，且每次渲染都要重复传；现在 WebView 同源加载、天然带缓存。
- `installedApps()` 返回的是 `[{pkg,label,icon}]`（URL 很轻），并顺带把图标文件生成好，前端拿到 URL 立刻可显示。
- 缓存被系统清理时 `<img onerror>` 调 `appIconFor(pkg)` 让原生重新导出并带时间戳重试；仍失败才显示**该应用自己的名字**（不是统一图标）并提示重新添加。

## 5. 启动链路与权限

```
点图标 → launchApp(pkg) → getLaunchIntentForPackage(pkg)
       → FLAG_ACTIVITY_NEW_TASK → startActivity
       → 返回 false 时提示「可能已卸载，可点 × 从速达移除」
```

Android 11+（targetSdk 32）默认限制包可见性，Manifest 里声明
`<intent><action MAIN/><category LAUNCHER/></intent>` 后才能枚举第三方应用；
只查启动入口，没有申请 `QUERY_ALL_PACKAGES`。应用列表与图标全程只在本机使用，不上传、不入同步。

## 6. 图标布局不越界

`.app-grid` 用 `grid-template-columns: repeat(auto-fill, minmax(64px, 1fr))`：
列数随容器宽度自动变化，放不下就换行；`1fr` 保证列宽永远按容器分配而不会撑宽容器。
再加 `width/max-width:100%`、`box-sizing:border-box`、`overflow:hidden`，
`.app-tile / .app-btn` 设 `min-width:0 / max-width:100% / overflow:hidden`，
`.app-label` 单行省略；`.res-scroll` 设 `overflow-x:hidden`。
端到端用例在 360px 视口下放 12 个应用，实测 3 行、0 个越界元素。

## 7. 已知边界（如实说明）

- 手机应用列表是**本地快照**：应用被卸载后图标仍在，点击会失败并提示移除，不会自动清理；最多 200 个。
- 只能添加「有 LAUNCHER 入口」的应用；没有启动入口的系统组件/服务不会出现在选择列表里。
- 个别应用取不到图标时按第 4 节的兜底处理，仍不显示统一占位图标。
- `resources` 集合与 PC 的同步协议（PROTO 2、COLS 五个集合）**完全没改**，旧数据、旧配对、PC 端行为保持兼容。
- 图标缓存在应用私有 cache 目录，系统清理缓存后会自愈重取；卸载 App 则手机应用列表随之消失（它只存本机）。
