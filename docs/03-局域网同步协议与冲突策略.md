# 局域网同步协议与冲突策略（v1）

> 目标：让 x-hub 桌面端与 Android 端在**同一局域网**内双向同步待办；任一端离线时都能独立工作，恢复后自动收敛。
> 设计取向：**本地优先（local-first）+ 单一中枢（hub）+ 记录级 LWW**。宁可简单可验证，不做字段级合并。

---

## 1. 角色与拓扑

```
┌──────────────┐        HTTP/SSE (TCP 47821)        ┌──────────────┐
│  Android App │ ──────────────────────────────────▶ │  x-hub 扩展   │
│  本地 SQLite  │ ◀────────────────────────────────── │  Node 中枢    │
└──────────────┘                                     └──────┬───────┘
        ▲                                                   │ 反代 / 桥
        │ 手机热点 / 路由器同一网段                            ▼
        │                                            ┌──────────────┐
        └──────── 可选：第二台手机 ────────────────────│ 宿主待办库     │
                                                     └──────────────┘
```

| 角色 | 职责 | 不做 |
|---|---|---|
| **Hub**（扩展 service 后端） | 权威变更日志、序号分配、冲突判定、设备与令牌管理 | 不直接读写宿主 SQLite |
| **Android** | 本地数据库 + 增量同步 + 离线队列 | 不直连宿主 |
| **宿主桥接器**（扩展 view 前端） | 宿主待办 ↔ Hub 的搬运（`todos.list` / `create` / `update` / `toggle` / `delete`） | 不做冲突判定 |

> Hub 是唯一权威。Android 与 PC 都是它的对等客户端，只是 PC 侧多一层「宿主待办」的适配。

## 2. 传输层

| 项 | 选择 | 理由 |
|---|---|---|
| 协议 | HTTP/1.1 + JSON（UTF-8） | 无依赖、可 curl 调、Android/Node 都原生支持 |
| 端口 | 固定 **47821**（`backend.port: 47821`） | 端口固定，手机记住一次即可长期直连；防火墙规则也按端口持久化 |
| 监听 | `0.0.0.0`（`backend.host`），需 `network` 权限 | 平台一等公民能力，宿主自动加 TCP 入站规则 |
| 加密 | 无 TLS，改由 **Bearer Token + 配对码** 做准入 | 局域网自签证书体验极差；数据是待办，敏感度可控，交付文档中明示 |
| 推送 | **SSE**（`GET /api/v1/stream`） | 单向推送足够；比手写 WebSocket 帧解析可靠，且断线由 `EventSource` 自动重连 |
| 保底 | 客户端轮询（30s） | 老设备/省电模式禁 SSE 时仍能同步 |

### 2.1 通用约定

- 所有响应 `Content-Type: application/json; charset=utf-8`（SSE 除外）。
- 时间统一**毫秒 Unix 时间戳**（整数），不用字符串日期。
- 未知字段忽略；缺字段按默认值处理（向前兼容）。
- 请求体上限 1 MB；超限 `413`。
- 幂等：`POST /sync` 可重放，重复 change 只按 HLC 判胜负，不产生重复记录。

## 3. 配对与鉴权

### 3.1 配对流程

```
PC(扩展页)                         Hub                        Android
   │  显示 6 位配对码 + 地址          │                            │
   │──────────────────────────────▶│                            │
   │                                │◀── POST /api/v1/pair ──────│
   │                                │    {code, device}          │
   │                                │─── 200 {token, hubId} ────▶│
```

- 配对码：6 位数字，**5 分钟**有效，一次性；连续 5 次错误锁定该 IP 10 分钟。
- 令牌：32 字节随机 hex，服务端只存 `sha256(token)`；同一 `deviceId` 重新配对会**吊销旧令牌**。
- 令牌无过期时间，但可被 PC 端「移除设备」即时吊销。
- 设备名默认取 `Build.MODEL`，可改。

### 3.2 请求头

```http
Authorization: Bearer <token>
X-Hub-Device: <deviceId>
X-Hub-Proto: 1
```

缺令牌或令牌无效 → `401 {"code":"UNAUTHORIZED"}`；设备被吊销 → `403 {"code":"DEVICE_REVOKED"}`。

### 3.3 局域网内互相可见性说明

服务监听 `0.0.0.0`，同网段任何设备都能**尝试**连接，但没有令牌读不到任何数据（除 `/ping`）。这是明确的安全边界，交付文档与授权弹窗文案都要写清楚。

## 4. 数据模型

### 4.1 记录

```jsonc
{
  "id": "h:12",                 // 全局 id：h:<宿主数字 id> 或 a:<uuidv4>
  "title": "写周报",
  "done": false,
  "priority": 0,                // 0 普通 / 1 重要 / 2 紧急
  "dueAt": 1762416000000,       // null = 未排期
  "remindAt": null,
  "description": "",
  "parentId": null,             // 指向另一条记录 id
  "pinned": false,
  "repeatMode": "once",
  "createdAt": 1762330000000,
  "completedAt": null,
  "deleted": false,             // 墓碑标记
  "hlc": "0000018f2e5c3a10-0003-7f3a",
  "seq": 128                    // 服务端分配，客户端只读
}
```

### 4.2 HLC（混合逻辑时钟）

排序键，解决「手机时钟不准」导致的错误覆盖。

```
格式：<16 位十六进制物理毫秒>-<4 位十六进制计数>-<4 位设备短码>
比较：先比 t，再比 c，最后比设备短码（字典序）→ 全序且确定
```

本地事件：

```
t' = max(now, lastT)
c' = (t' == lastT) ? lastC + 1 : 0
```

收到远端事件：

```
t' = max(now, lastT, remoteT)
if t' == lastT && t' == remoteT: c' = max(lastC, remoteC) + 1
elif t' == lastT:               c' = lastC + 1
elif t' == remoteT:             c' = remoteC + 1
else:                           c' = 0
```

> 选 HLC 而不选「服务器时间戳」的理由：离线编辑必须先落本地，若用服务器时间，离线期间的多次编辑会全部塌成同一时刻，无法定序。

## 5. 接口

### 5.1 `GET /api/v1/ping`（免鉴权）

```json
{ "app": "xhub-todo-relay", "proto": 1, "hubId": "8f3c…", "hubName": "DESKTOP-01",
  "needsPair": true, "recordCount": 42, "seq": 128, "serverTime": 1762416000000 }
```

用途：连通性探测、地址校验、界面显示端点信息。

### 5.2 `POST /api/v1/pair`

```jsonc
// 请求
{ "code": "482913", "device": { "id": "and-7f3a…", "name": "Pixel 8", "platform": "android", "appVersion": "1.0.0" } }
// 响应
{ "token": "9f2c…", "hubId": "8f3c…", "deviceId": "and-7f3a…", "proto": 1, "serverTime": 1762416000000, "seq": 128 }
```

错误：`400 INVALID_CODE` / `429 TOO_MANY_ATTEMPTS` / `409 DEVICE_LIMIT`（默认上限 8 台）。

### 5.3 `GET /api/v1/snapshot`（鉴权）

首次同步或 `sinceSeq` 已过期时使用。

```jsonc
{ "seq": 128, "serverTime": 1762416000000, "records": [ /* 全部未删除 + 7 天内墓碑 */ ] }
```

### 5.4 `POST /api/v1/sync`（鉴权）—— 主通道

一次往返完成「推 + 拉」。

```jsonc
// 请求
{
  "deviceId": "and-7f3a",
  "sinceSeq": 42,
  "changes": [ /* 本地脏记录（含 hlc） */ ],
  "limit": 500
}
// 响应 200
{
  "seq": 128,
  "serverTime": 1762416000000,
  "applied": 3,
  "rejected": [ { "id": "h:12", "reason": "STALE", "winnerHlc": "0000018f…" } ],
  "conflicts": [ { "id": "h:12", "loser": "and-7f3a", "localHlc": "…", "remoteHlc": "…" } ],
  "changes": [ /* seq > sinceSeq 的记录，按 seq 升序 */ ],
  "hasMore": false,
  "resyncRequired": false
}
```

- `applied`：被接受的条数（服务端据此分配新 seq）。
- `rejected`：本地版本更旧，未被采纳；客户端应用响应里的 `changes` 覆盖本地。
- `conflicts`：同一记录双方都改过且**都被采纳过**的情形，供 UI 展示「已按最新修改合并」。
- `resyncRequired: true`：`sinceSeq` 早于日志保留窗口，客户端应改走 `GET /snapshot`。

### 5.5 `GET /api/v1/stream`（鉴权，SSE）

```
event: change      data: {"seq":129,"id":"h:12"}
event: peer        data: {"deviceId":"and-7f3a","online":true}
event: ping        data: {"serverTime":…}
```

客户端收到 `change` 只需触发一次 `POST /sync`（不解析内容，避免两套合并逻辑）。

### 5.6 仅本机可用的桥接接口

这几个只允许来自 `127.0.0.1`（宿主的 `/svc/` 反代）：`POST /api/local/ingest`、`GET /api/local/outbound`、`POST /api/local/ack`、`POST /api/admin/*`。非回环来源一律 `403 LOCAL_ONLY`。

### 5.7 错误码总表

| code | HTTP | 含义 | 客户端动作 |
|---|---|---|---|
| `UNAUTHORIZED` | 401 | 无/错令牌 | 转配对页 |
| `DEVICE_REVOKED` | 403 | 设备被移除 | 清令牌，转配对 |
| `LOCAL_ONLY` | 403 | 本机接口被远端调用 | 忽略 |
| `INVALID_CODE` | 400 | 配对码错误 | 提示重输 |
| `TOO_MANY_ATTEMPTS` | 429 | 试错过多 | 倒计时 |
| `BAD_REQUEST` | 400 | 结构不合法 | 记日志，不重试 |
| `RESYNC_REQUIRED` | 409 | 游标过期 | 拉快照 |
| `PAYLOAD_TOO_LARGE` | 413 | 超 1 MB | 分批 |
| `INTERNAL` | 500 | 服务端异常 | 退避重试 |

## 6. 冲突处理策略

### 6.1 判定

同一 `id` 在被同步双方都产生了**不同 hlc** 的修改，即为一次冲突。

### 6.2 解决：记录级 LWW

```
win(a, b) = compare(a.hlc, b.hlc) > 0 ? a : b      // 平局比设备短码，结果确定
```

不做字段级合并，理由（如实写明）：

1. 宿主 `todos.update` 是**全量覆盖**，字段级合并会产生「标题来自 A、截止时间来自 B」的中间态，再写回宿主时无法验证其业务合法性。
2. 字段级合并需要 base 版本（三方合并），而宿主不保留历史版本。
3. 待办是短文本、低并发场景，LWW 的语义损失远小于复杂度收益。

### 6.3 冲突可回溯

每次 LWW 覆盖都写一条冲突日志（保留 7 天 / 最近 200 条）：

```jsonc
{ "at": 1762416000000, "id": "h:12", "fieldSummary": "title, dueAt",
  "winner": { "device": "and-7f3a", "hlc": "…", "record": {…} },
  "loser":  { "device": "pc-host", "hlc": "…", "record": {…} } }
```

PC 端「同步」页提供「冲突记录」列表，可一键**恢复败方版本**（恢复动作本身是一次新修改，会正常参与后续同步）。

### 6.4 删除

- 删除 = 写墓碑（`deleted: true` + 新 hlc），不是物理删。
- 墓碑保留 **30 天**后清理；清理前客户端只要同步过就一定见过它。
- 宿主侧 `parent_id` 有级联删除：删除父待办时，桥接器必须**先**为所有子待办各写一条墓碑，否则子条目会在下次 ingest 时「复活」。

## 7. 同步流程

### 7.1 增量同步（常态）

```
Android                                  Hub
   │ ① 收集 dirty（本地修改，按 hlc 升序）   │
   │──── POST /sync {sinceSeq, changes} ──▶│
   │                                       │ ② 逐条 LWW 合并，接受则分配 seq++
   │                                       │ ③ 取 seq > sinceSeq 的记录
   │◀─── {seq, applied, changes, …} ───────│
   │ ④ 事务内：应用 changes + 更新 lastSeq   │
   │    清 dirty（被 accepted 的）           │
   │ ⑤ 若 hasMore → 立即再来一轮             │
```

- 客户端 `lastSeq` 与 dirty 标记必须**同一事务**落盘，否则断电会产生重复推送或漏推。
- 每轮 `limit` 500；`hasMore` 为真就继续，直到 false。

### 7.2 首次 / 重装同步

`GET /snapshot` → 全量替换本地（保留本地 dirty 的，再走一次 `POST /sync` 推上去）。

### 7.3 宿主桥接（PC 侧）

```
view 前端（建议常驻后台）
  每 15s 或收到 change 事件：
  ① hostSnapshot = await xhub.data.todos.list()
     POST /api/local/ingest {records, hostSeq}
     → Hub 用 version 变化判定「宿主侧有新编辑」，生成 pc-host 的 change
  ② out = GET /api/local/outbound?since=<cursor>
     → 对每条：create / update(expectedVersion) / toggle / delete
     → POST /api/local/ack {cursor, results}
  ③ 冲突：VERSION_CONFLICT → 重读一次再写；仍冲突则比较宿主 updated_at 与远端 hlc.t 的物理时间，晚者胜并记日志
```

> **明确的能力边界**：前端页面未打开时，Android 的修改只会停留在 Hub，**不会**写进宿主待办。要消除这个窗口，需用户在扩展设置里开启「常驻后台」。这是宿主的既定机制，不是本扩展能绕过的。

## 8. 离线 / 联机状态机

### 8.1 Android

```
        ┌──────────┐  探测成功+已配对   ┌──────────┐  有 dirty   ┌──────────┐
        │ OFFLINE  │──────────────────▶│  ONLINE  │────────────▶│ SYNCING  │
        └──────────┘◀──────────────────└──────────┘◀────────────└──────────┘
             ▲        连续 3 次失败           ▲  完成                 │
             │                               └───────────────────────┘
             │ 未配对 / 令牌失效
        ┌──────────┐
        │ UNPAIRED │
        └──────────┘
```

| 状态 | 触发 | UI | 数据行为 |
|---|---|---|---|
| `UNPAIRED` | 无令牌 | 显示配对引导 | 纯本地可用 |
| `OFFLINE` | 网络不可达 / 探测失败 | 灰点「离线」 | 写入只落本地并标 dirty |
| `ONLINE` | `/ping` 成功且鉴权通过 | 绿点「已连接」 | 空闲时 30s 心跳 |
| `SYNCING` | 有 dirty 或收到 change | 蓝点「同步中」 | 推拉一轮 |
| `CONFLICT` | 响应含 conflicts | 橙点「N 条冲突」 | 仍继续同步，仅提示 |

切换规则：

- **写永远先落本地**，任何状态下都不阻塞输入。
- 本地修改后 800ms 防抖触发一次 sync（若 ONLINE）。
- 失败退避：2s → 4s → 8s → 16s → 32s → 60s 封顶，±20% 抖动；连续 3 次失败转 OFFLINE。
- 立即重试的时机：应用回到前台、网络从无到有、用户下拉刷新、SSE 收到 change。
- 离线期间不产生任何后台网络请求（省电）。

### 8.2 PC

| 情形 | Hub | 宿主待办 | 说明 |
|---|---|---|---|
| x-hub 运行 + 扩展页打开 | 在线 | 双向实时 | 完整能力 |
| x-hub 运行 + 扩展页关闭 | 在线 | **只读滞后** | Android 改动堆在 Hub，等页面打开后回灌 |
| x-hub 未运行 | 离线 | — | Android 转 OFFLINE，纯本地 |

## 9. 性能与容量

| 指标 | 目标 | 做法 |
|---|---|---|
| 单次同步耗时 | < 300ms（1000 条以内，局域网） | 增量 + 500 条分页 |
| 支持记录数 | 5,000 条 / 设备 | 全量快照 < 2.5 MB，压缩后再传（gzip） |
| 变更日志保留 | 2,000 条 或 30 天 | 超出则要求 `resync` |
| 服务端内存 | < 80 MB | 全部状态在内存 + 落盘 JSON 快照 |

## 10. 安全边界（交付时必须告知用户）

1. 局域网内**任何设备**都能连到 47821 端口，但无令牌读不到数据。
2. 令牌明文存在手机本地（`SharedPreferences`）；丢失手机等于丢失访问权，可在 PC 端移除设备。
3. 明文 HTTP：同网段的抓包者可见内容。公共 Wi-Fi 下不建议开启。
4. 服务仅监听 `0.0.0.0`，不做公网穿透；如需跨网使用，请自行组 VPN（Tailscale 等），本扩展不提供。

## 11. 发现与配对（v2.8 补充）

### 11.1 为什么要单列

同步协议本身没问题，但「手机找不到电脑」是这类工具最高频的故障：一台开发机上常常同时有 WLAN、VMware VMnet1/8、
Hyper-V、WSL、TAP 虚拟网卡和 VPN，它们**都落在私网段**。任何「取第一个 192.168/10.x 地址」的做法都会有一半概率
把虚拟网卡给出去——手机路由不到，表现为一直转圈。

### 11.2 地址判定

| 步骤 | 规则 |
|---|---|
| 1 | 枚举所有非回环 IPv4，过滤 `169.254.*` 链路本地地址 |
| 2 | 对 `223.5.5.5:53` 建一个 UDP socket 并 `connect()`（不发包），`socket.address()` 即默认路由出口地址 |
| 3 | 出口地址命中者为主地址；未命中的按「物理网卡 > 虚拟网卡」排序，网卡名命中 VMware/Hyper-V/WSL/Docker/TAP/TUN/VPN 关键字降权 |
| 4 | 探测全部失败（离线/多网卡无默认路由）时，退化为排在最前的物理网卡 |

判定结果通过 `GET /api/v1/diag` 暴露，页面与文档、排障命令共用同一份结论，避免「界面一套、日志一套」。

### 11.3 配对载荷

| 版本 | 格式 | 说明 |
|---|---|---|
| v1/v2 | `xhub://2/<host:port>/<code>` | 单地址，仍兼容 |
| **v3** | `xhub://3/<code>/<host:port>,<host:port>,…` | 最多 6 个候选（客户端截断），主地址排第一，只放物理网卡 |

手机按「手输地址 → 候选列表」顺序 `ping`（`GET /api/v1/ping`，6s 超时）后 `pair`。配对码错误（`INVALID_CODE`）、
尝试超限（`TOO_MANY_ATTEMPTS`）、设备数满（`DEVICE_LIMIT`）属于**终态**，换地址也不会成功，应立即停并提示。

### 11.4 诊断命令

```bash
curl http://127.0.0.1:47821/api/v1/diag      # primary / defaultRoute / addresses[].virtual / verdict
curl http://<主地址>:47821/healthz            # 手机上打开，{"ok":true} 说明链路通
```
