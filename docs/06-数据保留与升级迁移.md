# 数据保留与升级迁移

> 问题：安装新版本后，旧版本的本地数据"被覆盖"了。
> 结论：**不是升级删了数据，而是页面 origin 变了，App 读到了另一个空存储分区。**

---

## 1. 根因

### 1.1 直接原因：本地端口每次都变，origin 跟着变

`AssetServer` 用系统分配端口：

```java
// 修复前
server = new ServerSocket(0, 16, InetAddress.getByName("127.0.0.1"));
```

`new ServerSocket(0)` 的意思是「随便给我一个空闲端口」。页面就从
`http://127.0.0.1:<这个端口>/index.html` 加载。

而浏览器的存储是**按 origin 隔离**的，origin = 协议 + 主机 + **端口**：

```
http://127.0.0.1:41234   ← 这次启动
http://127.0.0.1:52017   ← 下次启动（同一台手机、同一个 App）
```

上面两个在浏览器眼里是**两个完全不同的站点**。IndexedDB、localStorage、Cache 各存各的。
`core.js` 里 `indexedDB.open('todolink', 2)` 在新 origin 下等于「第一次访问」——
它老老实实建了一个**全新的空库**。

于是现象就是：数据没了。**其实旧库还在磁盘上**（`app_webview/Default/IndexedDB/http_127.0.0.1_41234.indexeddb.leveldb`），
只是新 origin 读不到它。

### 1.2 为什么"升级"才暴露

冷启动就会发生，跟升级没有因果关系。只是：

- 平时 App 常驻后台（`launchMode="singleTask"`，返回键在首页才退出），进程不重启，origin 就不变；
- 装新版本必然杀掉进程重启一次 —— 于是这一次 origin 变了。

如果连续两次启动恰好拿到同一个端口（有可能，取决于内核分配策略），就不会丢。
这解释了为什么现象看起来是"偶发"的。

### 1.3 放大因素：丢掉的不只是记录，还有配对

`meta` 里存着电脑地址、配对令牌、同步游标。新 origin 下这些也是空的：

```js
// core.js::boot
const metas = await idbAll('meta')     // 空
if (S.meta.token) syncNow('boot')      // 没有 token，不执行
setStatus('offline', '未配对')
```

所以升级后看到的是「未配对 + 空列表」，而不是「数据在哪但读不出来」。
用户重新配对后，`pullSnapshot()` 从电脑把数据拉回来 —— 数据"又回来了"，
这进一步掩盖了真正的原因。

## 2. 排除了哪些常见猜测

| 猜测 | 是否成立 | 依据 |
|---|---|---|
| 应用升级会清 `/data/data/<pkg>/` | 否 | 同包名同签名的覆盖安装不动私有目录，Android 保证 |
| 代码里清了缓存 | 否 | 全工程没有 `clearCache` / `deleteDatabase` / `clearHistory` |
| IndexedDB 版本升级把旧表删了 | 否 | `onupgradeneeded` 只 `createObjectStore`，从不 `deleteObjectStore` |
| `allowBackup` 恢复把数据覆盖了 | 否 | 备份恢复只在换机/重装时触发，且与本问题无关 |
| 同步把本地覆盖了 | 部分 | 见 3.2，是次要风险，不是本次主因 |

---

## 3. 影响面

### 3.1 受影响

- 本地待办 / 笔记 / 便签 / 速达 / 提示词（IndexedDB `records`）
- 电脑配对信息、同步游标、AI 配置与密钥、主题设置、番茄钟状态（IndexedDB `meta`）
- 对话记录（`meta.aiMessages`）

**都是"读不到"，不是"被删"** —— 旧 origin 的数据仍在磁盘上。

### 3.2 次要风险（独立于本问题，但会造成同样的体感）

`pullSnapshot()` 用电脑快照**整体替换**本地集合：

```js
const map = {}
;(snap.records || []).forEach((r) => (map[r.id] = ...))
S.records.forEach((r) => {
  if (r.dirty && (!map[r.id] || map[r.id].hlc < r.hlc)) map[r.id] = r   // 只有脏数据被保留
})
S.records = Object.keys(map).map((k) => map[k])                        // 其余一律以快照为准
```

设计意图是对的（缺失 = 电脑上删了，靠墓碑同步）。但如果电脑端中枢数据丢了 / 换了电脑，
手机会跟着被清空，且本地干净数据没有反抗机会。

## 4. 方案对比

| 方案 | 做法 | 数据留存 | 改动量 | 风险 |
|---|---|---|---|---|
| **A 固定端口**（本次采用） | `ServerSocket(47830)` 起依次尝试，`setReuseAddress(true)` | 高（只要端口不被占就 100%） | 极小 | 端口被占用时仍会漂移 |
| **B 固定 origin** | `shouldInterceptRequest` 拦截 `https://appassets.androidplatform.net`，不再用本地 Socket | 100%（origin 永久固定） | 中 | 见下方 mixed content 问题 |
| **C 数据搬到原生** | IndexedDB → SQLite / 文件，经 bridge 读写 | 100%（与 origin 无关） | 大 | 要重写整个数据层与同步层 |

### 4.1 为什么本次选 A

- origin 的 scheme 保持 `http://127.0.0.1`，**不触发 mixed content**。
- 只改端口分配，页面、同步、AI 全都不用动。
- 端口被占用的概率极低（47830–47833 四个候选），且被占时页面会明确提示。

### 4.2 方案 B 的坑（重要，别直接抄）

固定 origin 通常写成 `https://appassets.androidplatform.net`。但页面里所有局域网请求是**明文 http**：

```js
fetch('http://' + host + path)        // core.js::http，host 是 192.168.x.x:47821
```

https 页面请求 http 资源 = mixed content，而当前 WebView 设置是：

```java
s.setMixedContentMode(WebSettings.MIXED_CONTENT_NEVER_ALLOW);
```

直接换 origin 会把**同步功能整个打死**。

要上 B 必须同时满足其一：
1. 把 `core.js::http()` 改成走原生桥（`native.streamHttp`）—— 好消息是它是**唯一出口**，
   全工程只有这一个函数发局域网请求，且没有用 `EventSource`（同步靠 30s 轮询），改造点收敛；
2. 或放宽为 `MIXED_CONTENT_ALWAYS_ALLOW`（安全降级，不推荐）。

### 4.3 方案 C 什么时候值得做

当满足任一条件时再迁移：需要存储超过 IndexedDB 配额、需要后台任务直接读写数据、
或者要彻底摆脱 WebView 存储策略。现阶段不划算。

## 5. 本次落地的改动（v2.4.1）

### 5.1 固定端口

```java
private static final int[] PREFERRED_PORTS = {47830, 47831, 47832, 47833};

int start() throws IOException {
    for (int port : PREFERRED_PORTS) {
        try { server = bind(port); break; } catch (IOException ignored) { }
    }
    if (server == null) {
        Log.w(TAG, "固定端口全部占用，回退临时端口；本次的本地数据分区会变");
        server = bind(0);
    }
    ...
}

private static ServerSocket bind(int port) throws IOException {
    ServerSocket s = new ServerSocket();
    s.setReuseAddress(true);   // 必须在 bind 之前，否则 TIME_WAIT 会让端口「看起来被占」
    s.bind(new InetSocketAddress(InetAddress.getByName("127.0.0.1"), port), 16);
    return s;
}
```

### 5.2 端口变了要说出来，不能静默丢

MainActivity 把上次端口记在 `SharedPreferences`，本次不同则置 `originSwitched`，
经桥暴露 `originChanged()` / `originPort()`；首页据此显示提示条：

> **本地存储分区已变化（端口 47830）**
> 旧版本的本地数据不会自动出现在这里。如果之前配对过电脑，到「我的 → 同步与设置」重新配对一次即可同步回来。

宁可让用户看到一句解释，也不要让它以为数据被删了。

## 6. 旧数据怎么救（迁移策略）

### 6.1 已配对过电脑的用户（绝大多数）

数据本来就在电脑中枢里，重新配对即回：

1. 装 v2.4.1
2. 「我的 → 同步与设置」重新扫码/输入配对码
3. `pullSnapshot()` 拉全量，待办/笔记/便签/速达/提示词全部回来

**注意会丢的**：AI Key、主题设置、番茄钟进度、对话记录——这些只存在本地，中枢不存。

### 6.2 纯本地、从未配对的用户

旧数据仍在磁盘的旧 origin 目录里，但**无法程序化枚举和迁移**：

- origin 由浏览器内部管理，JavaScript 没有"列出本应用所有 origin"的 API；
- 旧版本没有导出功能，无法让它把数据吐出来。

可走的路只有一条，且要用户配合：

1. 装回旧版本（同签名，可覆盖安装）
2. 旧版本仍用随机端口 → 也未必能打开当初那个 origin，**成功率不高**

所以现实结论：**这部分数据找不回来**。这也说明为什么"导出/导入"必须尽快补上（见 7.1）。

### 6.3 未来版本

origin 固定后，升级不再影响本地数据，无需迁移。

## 7. 长期建议

### 7.1 导出 / 导入（优先级最高）

设置里加「导出全部数据（JSON）」与「从 JSON 恢复」。它不依赖 origin、不依赖电脑，
是任何存储事故的最后一道兜底。建议字段：

```json
{ "app": "2.4.1", "exportedAt": 1793948400000, "records": [...], "meta": { "themeMode": "...", "accentColor": "..." } }
```

导出时剔除 `ptToken` / `aiKey` 等凭据，避免明文外泄。

### 7.2 快照骤降保护

`pullSnapshot()` 替换前先比对条数，跌幅超过阈值（如 80%）时要求用户确认：

```js
const before = S.records.filter((r) => !r.deleted).length
const after = (snap.records || []).length
if (before > 20 && after < before * 0.2 && !(await confirmAsync('电脑端数据明显变少…'))) return
```

防止"电脑端中枢被清空 → 手机跟着清空"。

### 7.3 DB 版本约定

- `DB_VER` 只增不减；
- `onupgradeneeded` 里**只允许** `createObjectStore` / `createIndex`，永不做 `deleteObjectStore` / `clear`；
- 需要改结构时用「新建 store + 双写 + 迁移 + 删旧 store（延迟一个大版本）」。

### 7.4 存储健康检查

设置页显示：库名、记录数、最近写入时间、当前 origin 端口。出问题时一眼能看出
"是数据没了，还是连到了另一个分区"。

## 8. 注意事项清单

**发布相关**

- 包名（`com.zhou.todolink`）与签名**都不能变**。变了只能卸载重装，私有目录连同数据一起没。
- 不要加 `android:clearTaskOnLaunch`、不要调 `WebView.clearCache(true)` / `clearHistory()`。
- `allowBackup="true"` 保留，但**不要依赖它**：跨设备恢复后 WebView 的存储目录可能不被采用，且 origin 端口不同也读不到。

**代码相关**

- 任何改变页面 origin 的改动（端口、scheme、host）都等于"换库"，必须配迁移或明确提示。
- 页面里新增的出站请求要考虑 mixed content：https origin 下不能打 http。
- 不要在 `boot()` 里做"空库就重建"的逻辑，会掩盖问题；空库要能区分「首次安装」和「换了分区」。

**验证相关**

- 装机验证顺序：装 v2.4.1 → 建几条数据 → 杀进程重开 → 数据仍在（端口应稳定在 47830）。
- 再装一次 v2.4.1（覆盖安装）→ 数据仍在。
- 用 `adb shell cat /data/data/com.zhou.todolink/app_webview/Default/IndexedDB/` 看一眼分区目录名，
  正常应只有一个 `http_127.0.0.1_47830.indexeddb.leveldb`；有多个说明历史上漂过。

---

## 9. 一句话总结

数据不是被覆盖的，是**页面换了 origin 就换了库**。
把端口固定住（本次已做），origin 就固定，数据就留得住；
已经丢的那批，配过电脑的重新同步即可，没配过的找不回来 —— 所以「导出/导入」应当尽快补上。
