## 一、P0：第一周必须完成（7 项）

### P0-1 本机接口可被任意网页 CSRF（index.js:90-93、325-336）

**现状**
- `isLocal()` 只看 `req.socket.remoteAddress`。恶意网页由本机浏览器发起请求，`remoteAddress` 同样是 `127.0.0.1`，这道校验形同虚设。
- `send()` 与 OPTIONS 一律返回 `Access-Control-Allow-Origin: *`，且 `Allow-Methods` 覆盖 GET/POST/PUT/DELETE，预检无条件通过。
- `/api/local/*`、`/api/admin/*` 不校验任何令牌。

**攻击链（完整可执行）**
1. 用户打开任意恶意页面；
2. 页面 `fetch('http://127.0.0.1:47821/api/admin/state')` —— 简单请求无需预检，`*` 让响应可读 → 拿到 6 位配对码、设备列表、全部记录；
3. 有了配对码，页面直接 `POST /api/v1/pair` 换取长期令牌，此后永久读写全部数据；
4. 即使不配对，`POST /api/admin/revoke`、`/api/admin/rotate-code` 也能造成拒绝服务。

**修复（三层，缺一不可）**

① 收紧 CORS，按前缀分流：

```js
// 手机端靠 Authorization 头里的 Bearer 令牌鉴权，不带 Cookie，不存在 CSRF；
// 本机接口则必须按同源收紧。
function corsHeaders(req, pathname) {
  const origin = req.headers.origin
  if (pathname.startsWith('/api/v1/')) {
    return { 'Access-Control-Allow-Origin': '*' }
  }
  // 本机接口：无 Origin（同源 GET / 非浏览器客户端）或白名单内才放行
  if (!origin) return {}
  const allowed = new Set([`http://127.0.0.1:${PORT}`, `http://localhost:${PORT}`])
  if (allowed.has(origin)) {
    return { 'Access-Control-Allow-Origin': origin, Vary: 'Origin' }
  }
  return null // 调用方据此返回 403
}
```

② OPTIONS 不再无条件 204，先过 `corsHeaders`，为 `null` 直接 403。

③ 本机接口强制自定义请求头：

```js
const LOCAL_ONLY = ['/api/local', '/api/admin']
// 自定义头会触发预检，跨站无法伪造；同源请求天然带得上
const localPrefix = LOCAL_ONLY.find((p) => pathname.startsWith(p))
if (localPrefix) {
  if (!isLocal(req)) return fail(res, 403, 'LOCAL_ONLY')
  if (req.method !== 'OPTIONS' && req.headers['x-hub-local'] !== '1') {
    return fail(res, 403, 'LOCAL_HEADER_REQUIRED')
  }
}
```

页面侧统一在 `svc()` 里加 `'X-Hub-Local': '1'`（`view/app.js:40`）。

**为什么这样够**：攻击者能发简单请求，但发不出带自定义头的跨站请求——预检会被 ② 拦掉；即便绕过预检（老浏览器），响应也读不到（① 不给 `*`）。

**验证**：在 `_tools` 下加一条用例，起服务后用 `page.goto('about:blank')` 再 `fetch` 目标，断言被 403；同时断言扩展自身页面功能不受影响。

### P0-2 `/api/ai/chat` 是 SSRF 跳板且已无人使用（index.js:613-656）

**现状**：`body.baseURL` 原样拼 `/chat/completions` 后 `fetch`，无协议校验、无网段校验、无重定向限制。可打 `http://169.254.169.254/latest/meta-data/`、内网任意主机、本机其它端口。手机端已改走 `native.js` 的 `streamHttp`，此端点**零调用方**。

**修复：直接删除**（首选）

删除 613-656 整段，并把 `docs/05` 第 92 行那条历史链路标注为「已移除（v2.2 起手机端直连）」——该文档 195 行已说明现状，只需把旧图注同步掉，避免后人按图施工。理由：无调用方，保留即负债；任何"加白名单"的方案都比删除多一层绕过风险。

若确需保留（例如将来做 PC 端 AI 代理），必须同时满足：

```js
const net = require('net'), dns = require('dns').promises
const BLOCK = [
  /^127\./, /^10\./, /^192\.168\./, /^169\.254\./, /^0\./,
  /^172\.(1[6-9]|2\d|3[01])\./, /^100\.(6[4-9]|[7-9]\d|1[01]\d|12[0-7])\./,
]
async function assertPublicUrl(raw) {
  const u = new URL(raw)
  if (u.protocol !== 'https:') throw new Error('ONLY_HTTPS')
  const ips = await dns.lookup(u.hostname, { all: true })
  for (const { address } of ips) {
    if (net.isIP(address) && (BLOCK.some((r) => r.test(address)) || address === '::1' || address.startsWith('fc') || address.startsWith('fd')))
      throw new Error('PRIVATE_ADDRESS')
  }
  return u
}
// fetch 时必须 redirect: 'manual'，且连接固定到已校验的 IP，防 DNS rebinding
```

**验证**：`curl -X POST /api/ai/chat -d '{"baseURL":"http://169.254.169.254"}'` 期望 404（已删除）或 400 `PRIVATE_ADDRESS`。

### P0-3 状态文件损坏即静默空库，且会被覆盖（store.js:76-86、97-108）

**现状**
```js
load() {
  try { return JSON.parse(fs.readFileSync(DATA_FILE,'utf8')) }
  catch (e) { if (e.code !== 'ENOENT') console.error('读取失败，按空库启动'); return null }
}
```
解析失败 → 返回 `null` → 构造器用 `emptyState()` → **第一次 `flush()` 就把空库写回去**，原文件永久丢失。日志只打一行，用户无感知。

**修复**

```js
load() {
  let raw
  try { raw = fs.readFileSync(DATA_FILE, 'utf8') }
  catch (e) { if (e.code === 'ENOENT') return null; throw e }   // 读不了 ≠ 空库

  try {
    const s = JSON.parse(raw)
    if (!s || typeof s !== 'object' || typeof s.records !== 'object') throw new Error('shape')
    return s
  } catch (e) {
    // 隔离坏文件，尝试备份，绝不静默重置
    const bad = `${DATA_FILE}.corrupt-${Date.now()}`
    fs.renameSync(DATA_FILE, bad)
    console.error(`[store] 状态文件损坏，已隔离到 ${bad}：${e.message}`)
    for (const bak of [`${DATA_FILE}.bak`]) {
      try {
        const s = JSON.parse(fs.readFileSync(bak, 'utf8'))
        if (s && typeof s.records === 'object') {
          console.error(`[store] 已从备份恢复（${Object.keys(s.records).length} 条记录）`)
          return s
        }
      } catch (_) {}
    }
    throw Object.assign(new Error('STATE_CORRUPT'), { code: 'STATE_CORRUPT' })
  }
}
```

`flush()` 在写新文件前先 `copyFileSync(DATA_FILE, DATA_FILE + '.bak')`，形成单代备份。

进程启动处捕获 `STATE_CORRUPT`：不退出，但**以只读模式启动**并把错误顶到 `/api/admin/state` 的 `fatal` 字段，页面用红条显示「本地库损坏，已隔离，请从 <path> 恢复」——宁可停写，也不能覆盖。

**验证**：写入半截 JSON → 重启 → 断言 `hub.json.corrupt-*` 存在、原数据未丢、HTTP 返回 `fatal`。

### P0-4 手机端把「被拒绝的修改」标记为已同步（android core.js:313-324）

**现状**
```js
if (r.hlc === p.hlc || rejected[p.id]) {
  r.dirty = 0          // ← 被服务端拒绝也清 dirty
  ops.push({ type: 'put', value: r })
}
```
服务端 `rejected` 表示「你的版本比服务端旧，未采纳」。清掉 `dirty` 后：本地不再重试；而 `applyIncoming` 里 `local.dirty && local.hlc > inc.hlc` 的保护又让远端版本进不来。结果是**这条修改两端都不生效、永远悬空**，且用户看不到任何提示。

**修复**

```js
const rejectedMap = {}
;(res.rejected || []).forEach((x) => (rejectedMap[x.id] = x))

pushed.forEach((p) => {
  const r = findRec(p.id)
  if (!r) return
  const rej = rejectedMap[p.id]
  if (rej) {
    // 不丢修改：转入冲突表，保留本地版本供用户选择
    addConflict({
      col: r.col, id: r.id, title: r.title,
      fields: [],                       // 与 P1-9 一并修
      winner: 'pc-host', loser: 'phone',
      localHlc: r.hlc, remoteHlc: rej.winnerHlc || '',
    })
    r.dirty = 0
    r.blocked = 1                       // 标记「已被覆盖」，UI 可提示
    ops.push({ type: 'put', value: r })
    return
  }
  if (r.hlc === p.hlc) {                // 只有确认写入成功才清 dirty
    r.dirty = 0
    ops.push({ type: 'put', value: r })
  }
})
```

同时 `applyIncoming` 的保护条件要放行 `blocked` 记录（`local.dirty && !local.blocked && local.hlc > inc.hlc`），让服务端胜出版本真正落地。

**验证**：构造「手机改 A、PC 同时改 A 且 HLC 更大」→ 同步 → 断言手机侧出现冲突条目、`blocked=1`、远端版本已写入，且本地原值仍可在冲突详情里看到。

### P0-5 HLC 缺少 maxDrift，异常时间可把 hub 时钟推偏（hlc.js:63-80）

**现状**：`observe()` 里 `const t = Math.max(now, this.t, p.t)`，`p.t` 完全信任远端。一台把系统时间调到 2099 年的设备（或恶意构造的 `hlc` 字段）会让 `this.t` 跳到极远未来，此后**本机产生的所有新时间戳都小于它** → PC 端每次修改都被判 STALE，且没有任何提示。

**修复**

```js
const MAX_DRIFT_MS = 5 * 60 * 1000

observe(hlc, nowMs) {
  const p = parse(hlc)
  if (!p) return { rejected: true, reason: 'BAD_FORMAT' }
  const now = typeof nowMs === 'number' ? nowMs : Date.now()
  if (p.t > now + MAX_DRIFT_MS) {
    return { rejected: true, reason: 'FUTURE_DRIFT', drift: p.t - now, remoteT: p.t }
  }
  if (p.t < now - 365 * 24 * 3600 * 1000) {
    return { rejected: true, reason: 'ANCIENT', remoteT: p.t }
  }
  // …原逻辑不变
  return { rejected: false }
}
```

三点配套：

1. `next()` 加本地单调保护：记录 `this.lastPhysical`，`now = Math.max(Date.now(), this.lastPhysical)`，防本地时钟回拨；
2. `observe` 的返回值必须被调用方处理——`store.merge()` 遇到 `rejected` 时**不采纳该记录**，写一条 `clock-anomaly` 冲突（含设备名、偏差毫秒），让用户在冲突面板看到「某设备时间异常，已拒绝其修改」；
3. `/api/v1/sync` 返回 `serverTime`，手机端据此校正本地时间偏移（每 10 分钟一次），从源头减少漂移。

**验证**：构造 `hlc = fmt(Date.now() + 86400e3, 0, 'dead')` 的入站记录 → 断言未被采纳、冲突表出现条目、本机后续 `next()` 仍单调递增。

### P0-6 ★ 配对码「超限」只提示不封禁（store.js:392-401）

**现状**
```js
if (String(code) !== p.code) {
  p.attempts += 1
  return { ok: false, reason: p.attempts >= 5 ? 'TOO_MANY_ATTEMPTS' : 'INVALID_CODE' }
}
return { ok: true }        // ← attempts 已 >5 时，猜对依然成功
```
`TOO_MANY_ATTEMPTS` 只是返回文案，没有真正拒绝。6 位码 90 万种、5 分钟窗口、无速率限制——配合 P0-1，恶意网页可在本机浏览器里**无限枚举**直到命中。

**修复**

```js
verifyCode(code, remote) {
  const p = this.state.pair
  if (!p) return { ok: false, reason: 'INVALID_CODE' }
  if (p.expiresAt <= Date.now()) return { ok: false, reason: 'EXPIRED' }
  if (p.attempts >= MAX_PAIR_ATTEMPTS) {      // 先判后比，封禁期内一律拒绝
    return { ok: false, reason: 'TOO_MANY_ATTEMPTS' }
  }
  if (!timingSafeEqualStr(String(code), p.code)) {
    p.attempts += 1
    this.scheduleSave()
    return { ok: false, reason: p.attempts >= MAX_PAIR_ATTEMPTS ? 'TOO_MANY_ATTEMPTS' : 'INVALID_CODE' }
  }
  return { ok: true }
}
```
`MAX_PAIR_ATTEMPTS = 5`。超限后**作废当前码**（`this.state.pair = null`），强制用户点「换配对码」，把枚举成本抬到「每次重试都要人点一下」。

再用 `timingSafeEqualStr`（等长 hash 后 `crypto.timingSafeEqual`）消除逐字符比较的时间侧信道。

**验证**：连续错 5 次后，第 6 次即使输对也返回 `TOO_MANY_ATTEMPTS`，且码已失效。

### P0-7 ★ 落盘失败后 dirty 已被清空，永不重试（store.js:97-108）

**现状**
```js
flush() {
  if (!this.dirty) return
  this.dirty = false        // ← 先清标志
  try { …writeFileSync…; …renameSync… }
  catch (e) { console.error('落盘失败:', e.message) }   // ← 失败也不恢复
}
```
磁盘满、权限变更、杀软锁文件时，写失败 → 标志已清 → 之后所有 `scheduleSave()` 都因 `dirty=false` 提前返回 → **直到下一次 `commit()` 才重新置脏，期间全部改动没有落盘**。进程若此时退出，数据静默丢失。

**修复**

```js
flush() {
  if (!this.dirty) return
  try {
    fs.mkdirSync(DATA_DIR, { recursive: true })
    const tmp = DATA_FILE + '.tmp'
    fs.writeFileSync(tmp, JSON.stringify(this.state))
    fs.renameSync(tmp, DATA_FILE)
    this.dirty = false           // 成功后才清
    this.saveFails = 0
  } catch (e) {
    this.saveFails = (this.saveFails || 0) + 1
    console.error(`[store] 落盘失败（第 ${this.saveFails} 次）:`, e.message)
    this.emit('save-error', { message: e.message, fails: this.saveFails })
    clearTimeout(this.retryTimer)
    this.retryTimer = setTimeout(() => this.flush(), Math.min(30000, 1000 * 2 ** this.saveFails))
  }
}
```
并把 `save-error` 透出到 `/api/admin/state.fatal`，页面红条提示「本地库写入失败，改动可能未保存」。

**验证**：把 `DATA_DIR` 设为只读目录 → 改一条待办 → 断言 `dirty` 仍为真、重试定时器已排、接口返回 `save-error`。

## 二、P1：第一个月完成（11 项）

### P1-8 全量 JSON 落盘（store.js:97-108）

**现状**：每次落盘把整个 `state`（全部记录 + 4000 条 log + 冲突）`JSON.stringify` 后同步写盘。记录上千条时单次序列化可达数百毫秒，**阻塞事件循环**，期间所有 HTTP 请求与 SSE 心跳卡住；`writeFileSync` 同步 IO 进一步放大。

**修复（两步）**
1. **立即缓解**：改为异步写 + 单飞（并发调用复用同一个 promise），并把 `flush` 里的 `JSON.stringify` 结果长度记入日志，超过 8MB 时告警；
2. **结构性**：拆成「快照 + 追加日志」——`hub.snapshot.json`（每 200 次提交或 5 分钟全量一次）+ `hub.wal`（每次提交追加一行 `{seq,id,rec}`），启动时快照 + 重放 WAL；WAL 超过 20MB 触发压缩。这样单次写入只追加几百字节。

若允许引入依赖，直接用 `better-sqlite3` 更彻底（WAL 模式 + 事务），迁移脚本按 `col` 建表即可。

### P1-9 冲突记录没有字段差异（android core.js:366-368）

**现状**：`addConflict({… fields: [] })` 恒为空数组。PC 端 `store.logConflict` 会算 `diffFields`，手机端不会，两端冲突面板信息量不一致。

**修复**：手机端补一个与 PC 同构的 `diffFields(loser, winner)`，按集合的字段白名单逐个比较，输出 `['title','dueAt']` 这样的数组；冲突详情页据此高亮「哪几个字段冲突」。

### P1-10 description 被截到 200 字符（store.js:582）

**现状**：`description: String(r.description || '').slice(0, 200)`，而同函数里 `notes.content` 是 200000、`snippets.content` 是 20000。README 明确写「长标题长备注不截断」，`docs/04` Q2 也有对应验收项。超过 200 字的备注经 PC 端中转后**被静默截断**，属于数据损坏。

**修复**：统一成一张字段上限表，避免再次写错。

```js
const LIMITS = {
  'todos.title': 500, 'todos.description': 20000,
  'notes.content': 200000, 'notes.title': 200,
  'stickies.content': 20000,
  'snippets.content': 20000,
  'resources.name': 200, 'resources.target': 2000,
}
function clip(col, field, v) {
  const max = LIMITS[col + '.' + field]
  const s = String(v == null ? '' : v)
  if (max && s.length > max) {
    console.warn(`[store] ${col}.${field} 超长截断 ${s.length}→${max}`)
    return s.slice(0, max)
  }
  return s
}
```
截断时**必须告警**，不再无声。

### P1-11 ★ 服务端零超时配置，慢连接可拖垮进程（index.js:766-774）

**现状**：`server.listen()` 后未设任何超时。Node 默认 `headersTimeout=60s`、`requestTimeout=300s`、`keepAliveTimeout=5s`，但仍缺 `clientError` 处理与连接数上限；局域网内一台设备持续发半截头即可占住连接。

**修复**

```js
server.headersTimeout = 15000
server.requestTimeout = 30000
server.keepAliveTimeout = 5000
server.maxConnections = 64
server.on('clientError', (err, socket) => {
  if (socket.writable) socket.end('HTTP/1.1 400 Bad Request\r\nConnection: close\r\n\r\n')
})
```
SSE 长连接不受 `requestTimeout` 约束（响应已开始），无需特殊处理。

### P1-12 ★ 无速率限制（全局）

**现状**：`/api/v1/pair`、`/api/v1/sync`、`/api/v1/ping` 均无频控。配合 P0-1 可被本机任意网页高频打，也可被局域网设备刷。

**修复**：进程内滑动窗口，按 `remoteAddress + 路径前缀` 计数。

```js
const buckets = new Map()
function rateLimit(key, max, windowMs) {
  const now = Date.now()
  const b = buckets.get(key) || { n: 0, reset: now + windowMs }
  if (now > b.reset) { b.n = 0; b.reset = now + windowMs }
  b.n += 1
  buckets.set(key, b)
  return b.n <= max
}
// 建议阈值：pair 10/分、sync 120/分、其它 240/分；超限返回 429 + Retry-After
setInterval(() => { for (const [k, b] of buckets) if (Date.now() > b.reset) buckets.delete(k) }, 60000).unref()
```

### P1-13 kv.json 损坏静默重置（index.js:298-306）

**现状**：`kvLoad()` 解析失败直接 `kvCache = {}`，随后任何 `kvSave()` 都会把空配置写回，扩展的 `config`/`storage` 全部丢失。与 P0-3 同类，只是影响面小。

**修复**：复用 P0-3 的隔离 + 备份策略；解析失败时把文件改名 `kv.json.corrupt-*` 并置 `kvFatal` 标志，`/api/admin/state` 透出。

### P1-14 SSE 已实现但两端零接入（index.js:462-486）

**现状**：服务端 `/api/v1/stream` 完整（Bearer 鉴权、`hello` 事件、25 秒心跳、`close` 清理），但 `view/` 与 `android/.../www/` 全目录 `EventSource` 零命中。后果是 PC 端 4 秒轮询、手机端最坏 30 秒才感知改动，且轮询流量恒定。

**修复（两端 + 降级）**

PC 端（页面同源，无需令牌）：
```js
// index.js 增加 /api/local/stream，与 /api/v1/stream 同一套广播，但走 P0-1 的本机鉴权
function connectStream() {
  const es = new EventSource('/api/local/stream')
  es.addEventListener('change', () => { S.qrFor = ''; poll() })
  es.addEventListener('peer', poll)
  es.onerror = () => {            // 断线后自动重连，EventSource 内建；同时保留轮询兜底
    if (es.readyState === EventSource.CLOSED) setTimeout(connectStream, 5000)
  }
}
```
手机端（EventSource 不能设 Header，用查询参数）：
```js
if (!SYNC.es) {
  SYNC.es = new EventSource(`${origin()}/api/v1/stream?token=${encodeURIComponent(S.meta.token)}`)
  SYNC.es.addEventListener('change', () => scheduleSoon())
  SYNC.es.onerror = () => { /* 交给浏览器重连；连续失败 3 次则退回 30 秒轮询 */ }
}
```
配套：轮询间隔从 4 秒放宽到 30 秒作为兜底，SSE 正常时几乎不产生请求。

**收益**：改动感知从「最坏 30 秒」降到「亚秒级」，移动端待机功耗明显下降。

### P1-15 PC 端 `svc()` 无超时（view/app.js:40-56）

**现状**：`api.service.request()` 不带超时。服务进程卡死（如 P1-8 的阻塞）时，页面所有按钮永久 pending，`poll()` 每 4 秒再叠一层未完成请求。

**修复**：`svc()` 增加 8 秒 `Promise.race` 超时；`poll()` 加 `polling` 单飞标志，避免重叠。

### P1-16 ★ uncaughtException 只打日志，不落盘不退出（index.js:793）

**现状**：`process.on('uncaughtException', (e) => console.error(...))`。异常后进程处于不确定状态却继续服务，且未 `flush()`。

**修复**
```js
process.on('uncaughtException', (e) => {
  console.error('[todo-relay] uncaught:', e)
  try { store.flush() } catch (_) {}
  server.close(() => process.exit(1))
  setTimeout(() => process.exit(1), 1500)
})
process.on('unhandledRejection', (e) => console.error('[todo-relay] unhandledRejection:', e))
```
配合宿主的常驻能力自动拉起。

### P1-17 AssetServer 单线程，一个慢连接卡住全部（AssetServer.java:114）

**现状**：`while (running) { Socket s = server.accept(); handle(s) }` —— 串行处理。WebView 加载页面时并发拉取 `index.html`、多个 `.js`、`.css`，任何一个连接慢都会让后续资源排队；若某个连接不关闭，整个静态服务停摆。

**修复**
```java
private final ExecutorService pool = Executors.newFixedThreadPool(4);
while (running) {
    final Socket s = server.accept();
    pool.submit(() -> { try { handle(s); } catch (Throwable ignore) {} finally { try { s.close(); } catch (Throwable ignore) {} } });
}
```
并在 `handle` 里设 `s.setSoTimeout(5000)`，`stop()` 时 `pool.shutdownNow()`。

### P1-18 局域网明文 HTTP + 令牌明文存储

**现状**：协议为明文 HTTP，Bearer 令牌在每次请求头里裸传；手机端令牌存在 IndexedDB（未加密）。同网段抓包即可拿到长期令牌。

**修复（按成本排序）**
1. **立即**：令牌加过期（默认 30 天）+ 每次同步刷新 `lastSeen`，闲置设备自动失效；设置页提供「撤销全部设备」；
2. **短期**：改用 HMAC 签名请求（`X-Hub-Sign` = HMAC(token, timestamp + path + body)），令牌本身不上链路，抓包只能重放到 5 分钟窗口内；
3. **中期**：局域网内自签证书 + TLS（手机端首次配对时指纹确认，类似 SSH `known_hosts`）。

## 六、两点判断说明

1. **`/api/ai/chat` 建议删除而非加固**。加白名单要处理 DNS rebinding、重定向、IPv6 映射地址三类绕过，成本远高于收益；该端点当前零调用方，删除是最干净的收口。
2. **SSE 的优先级高于表面看起来的重要性**。它不只是"省流量"：当前手机端 30 秒轮询意味着用户改完 PC 上的待办，要等半分钟手机才变；而两端都已有完整实现，只差接线。这是全表投入产出比最高的一项，因此排进第一个月而非第一季度。
