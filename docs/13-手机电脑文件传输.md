# 手机 ⇄ 电脑 文件传输（v3.0.0）

> 状态：已实现并发布。APK `3.0.0`（versionCode 24）、扩展 `3.0.0`。
> 相关代码：`extensions/todo-relay/service/files.js`、`android/app/src/main/java/com/zhou/todolink/FileTransfer.java`、
> `android/.../pages/transfer.js`、`extensions/todo-relay/view/app.js`。

## 1. 功能范围

### 1.1 两个方向

| 方向 | 入口 | 落点 | 说明 |
| --- | --- | --- | --- |
| 手机 → 电脑 | 手机「我的 → 文件传输 → 选择文件」 | 电脑扩展数据目录 `.data/files/inbox/` | 电脑扩展页「收件箱」可见，可复制路径、删除 |
| 电脑 → 手机 | 扩展页「文件传输 → 选择文件发送到手机」 | 手机「下载/x-hub/」（Android 10+，MediaStore） | 手机「待接收」列出，需手动点「接收」 |

不做：公网中继、离线排队、断网自动续传（需要用户回到页面点一次）、目录同步、相册自动备份。

### 1.2 文件类型

不按扩展名拒绝，避免把「传个 apk / 脚本给同事」这类正常需求堵死；改为**分级标注 + 永不自动打开**：

| 分类 | 扩展名 | 界面表现 |
| --- | --- | --- |
| 图片 | jpg/jpeg/png/gif/webp/bmp/heic/heif/svg/avif | 图标 + 类型 |
| 视频 | mp4/mov/mkv/webm/avi/m4v/3gp | 同上 |
| 音频 | mp3/m4a/aac/wav/flac/ogg/opus/amr | 同上 |
| 文档 | pdf/doc/docx/xls/xlsx/ppt/pptx/txt/md/csv/rtf/epub | 同上 |
| 压缩包 | zip/rar/7z/tar/gz/bz2/xz | 同上 |
| 代码/文本 | js/ts/json/html/css/py/java/go/rs/sh/yml/yaml/xml | 同上 |
| **高风险** | exe/msi/bat/cmd/com/scr/pif/ps1/vbs/vbe/wsf/wsh/hta/jar/reg/lnk/apk/dll/sys | 电脑收件箱与手机界面都打「可执行」红标 |

两端都不会自动打开、自动安装或执行收到的文件；电脑端只提供「复制路径」，由用户自己在资源管理器里决定。

### 1.3 大小与数量限制

| 项 | 值 | 超限表现 |
| --- | --- | --- |
| 单文件 | **512 MiB** | 手机端选完即提示；服务端 413 `TOO_LARGE` |
| 空文件 | 拒绝 | 400 `BAD_SIZE` |
| 文件名长度 | 清洗后 ≤ 180 字节 | 自动截断保留扩展名 |
| 电脑侧总配额 | **2 GiB**（收件箱 + 待发送） | 507 `QUOTA_FULL`，提示先清理 |
| 条目数 | 300 | 超出后按「已终结的最旧」淘汰 |
| 待接收有效期 | 24 小时 | 过期后手机端不再显示，电脑侧标「已过期」 |
| 本地保留 | 14 天 | 到期自动删文件与元数据 |
| 磁盘余量 | 需 ≥ 文件大小 + 64 MiB | 507 `NO_SPACE` |
| 并发 | 手机单任务顺序上传；电脑页面串行发送；手机可同时收 + 发 | — |

## 2. 传输方式

**局域网直连，复用已有的配对关系（无账号、无云端）。**

| 方案 | 取舍 |
| --- | --- |
| 局域网直连（采用） | 复用 `host:port` 与 Bearer 令牌；不经过任何服务器；速度取决于 Wi-Fi |
| 二维码配对（已有） | 文件通道不另设配对，扫过一次码即可；新增设备仍需配对 |
| 账号绑定（不采用） | 会增加云依赖与合规面，当前产品定位是「两台自己的设备」 |

限制与提示：

- 手机与电脑需在同一网段；开启 AP 隔离、访客 Wi-Fi、只连 VPN 时会失败。
- 服务只监听 `0.0.0.0:47821`（可配置），不向公网暴露。
- 电脑端「设备」列表里每台设备有「文件 开/关」开关；关闭后该设备所有 `/api/v1/files/*` 返回 403 `FILE_FORBIDDEN`。

## 3. 断点续传与进度

### 3.1 分块

- 明文块 **2 MiB**；最后一块按余数。
- 服务端严格按块序落盘：`received` 必须是块边界，跳块返回 409 `OFFSET {expected}`。
- 手机 → 电脑：块写进 `.data/files/tmp/<id>.part`，完成后整文件 SHA-256 校验，再改名进 `inbox/`。
- 电脑 → 手机：手机把密文块解密后追加到 `cache/transfers/<id>.part`，完成后校验、发布到系统下载目录。

### 3.2 断点

| 场景 | 恢复方式 |
| --- | --- |
| 单块网络失败 | 原生按指数退避重试同一块，不回到已完成的块 |
| App 被杀 / 进程重启 | `.part` 保留；下次 `GET /status` 以实际文件长度为准恢复 `received` |
| 手机上传中断后重开页面 | 任务元数据（fileId / sha256 / uri）存在 `meta.transferJobs`，行内「续传」按钮带 `resumeId` 重新开始 |
| 手机下载中断 | `.part` 保留，重新点「接收」从已下载的块继续 |
| 电脑端页面刷新 | 未完成的本地发送任务仍在服务端 `index.json`，可重新发起；已进入「待接收」的不受影响 |

### 3.3 进度

- 原生每完成一块回调一次 `transfer` 事件：`{id, state, sent, total, pct, savedTo?}`。
- 页面按 `sent / total` 画进度条，显示「已传 / 总大小 · 百分比 · 预计剩余」。
- 电脑端页面上传按 1 MiB 小块推进，进度条按块数计算。
- 服务端向电脑页面推送 SSE `file` 事件（`progress` 按 5% 或 900ms 节流），避免大文件把推送打满。

## 4. 失败与重试

| 层 | 策略 |
| --- | --- |
| 手机原生每块 | 最多 **5 次**，退避 300ms × 2ⁿ；网络异常 / 5xx / 429 重试，4xx（413/409/422 等）立即失败 |
| 电脑页面上传 | 每块 **3 次**，同上退避 |
| 整文件校验失败 | 服务端清空 `.part`、`received=0`，返回 422 `HASH_MISMATCH`；界面提示重试（从头传） |
| 进度不一致 | 409 `OFFSET`，带 `expected`；客户端提示「断点位置不一致，请重新发送」 |
| 取消 | 手机 `cancelTransfer` → 服务端 `abort` 删除 `.part`；下载取消保留 `.part` 供续传 |
| 电脑端不可达 | 页面顶部红字「连不上电脑」，不影响已完成的同步；文件接口失败不阻塞待办同步 |

每个传输任务都有明确终态：`done` / `error` / `canceled`，不会出现「永远转圈」。

## 5. 安全与权限

### 5.1 鉴权

- 所有 `/api/v1/files/*` 必须带 `Authorization: Bearer <配对令牌>`；令牌只在配对时下发一次，电脑只存 `sha256(token)`。
- 设备维度开关 `allowFiles`；老版本设备没有该字段时按允许处理（`undefined !== false`）。
- `/api/local/files/*` 仅本机：`isLocal(req)` + `Sec-Fetch-Site` / `Origin` 校验，跨站拿不到响应。
- 限流：文件桶 900 次/分钟/IP；配对桶仍是 10 次/分钟。

### 5.2 输入校验

- 客户端文件名**从不参与路径拼接**；磁盘名固定为 `<transferId>__<清洗后的名字>`，`id` 必须匹配 `^[a-f0-9]{24}$`。
- 清洗：去控制字符、Windows 非法字符 `\ / : * ? " < > |`、首尾点与空格，处理 `CON/PRN/COM1…` 保留名，NFC 归一化。
- 体积、配额、磁盘余量、块长度、块序号全部服务端复核；客户端的 `size` 不可信。
- `GET /status` 只允许任务所属设备读取；`finishUpload` 只接受上传方令牌派生出的密钥。

### 5.3 权限与审计

- 电脑端「设备」面板可单独关闭某台设备的文件权限，关闭立即生效（下一次请求 403）。
- 收发完成写审计：`file-receive` / `file-send`，含设备 id、文件 id、文件名、时间；`/api/admin/audit` 可查。
- 可执行文件仅标注，不自动运行；手机端保存到系统下载目录，不申请「所有文件访问」权限。

### 5.4 威胁模型与边界

覆盖：同一 Wi-Fi 下的被动嗅探、块被篡改、跨传输重放、路径穿越、未配对访问、越权读他人任务、配额耗尽。
不覆盖：电脑已被攻陷（可读 `.data` 明文）、手机已 root、恶意文件本身的社会工程、流量分析。

## 6. 数据加密

链路是局域网明文 HTTP，加密在应用层完成：

```
key   = HKDF-SHA256(IKM = token, salt = transferId, info = "xhub-file-v1", L = 32)
nonce = SHA-256(transferId)[0..4] || uint64BE(chunkIndex)     // 12B
AAD   = "xhub-file-v1|" + transferId + "|" + chunkIndex + "|" + totalSize
算法  = AES-256-GCM，每块密文尾部 16B 认证标签
```

| 属性 | 说明 |
| --- | --- |
| 机密性 | 被动抓包只能看到密文；密钥来自配对令牌，不出现在 URL |
| 完整性 | 每块 GCM 认证 + 整文件 SHA-256 双重校验 |
| 抗重放 | nonce 绑定块序号；AAD 绑定任务 id 与总长，换任务/换位置即失败 |
| 密钥轮换 | 吊销设备并重新配对即换新令牌；旧令牌派生的密钥立即失效 |
| 静态数据 | 电脑 `.data/files` 为明文（用户自己的磁盘）；手机落在系统下载目录。**未做磁盘加密**，需要的话由系统级全盘加密承担 |

实现一致性：Node 与 Java 两侧用同一组测试向量对拍（见 §9），密钥、nonce、AAD、密文逐字节相同。

## 7. 界面与流程

### 7.1 电脑端（扩展视图）

```
[文件传输]  1.2 GB / 2.0 GB · 单文件上限 512 MB        清空待接收
 ┌ 选择文件发送到手机 ┐  拖进来也可以 · 分块断点 · AES-256-GCM
 │ 上传进度条（按文件）│
 ├ 待接收（等待手机收）┬ 收件箱（手机发来的）┤
 │ 季度周报.pdf  删除  │ 旅行照片.zip  复制路径 删除 │
 └────────────────────┴──────────────────────┘
```

1. 点「选择文件」或把文件拖进虚线区（支持多选，串行发送）。
2. 每个文件显示 0–100% 进度；完成后进入「待接收」，状态为「等待手机接收」。
3. 手机接收后状态变「已送达 HH:MM:SS」；拒收显示「手机已拒收」；24 小时未收显示「已过期」。
4. 「收件箱」显示手机发来的文件，含来源设备、时间、大小、风险标记；可「复制路径」「删除」「清空」。
5. 「设备」面板每台设备旁有「文件 开/关」，可随时掐断某台设备的文件能力。

### 7.2 手机端（我的 → 文件传输）

```
[电脑：192.168.1.5:47821]  ● 在线
同一 Wi-Fi 直传 · AES-256-GCM · 断点续传

[发送到电脑]  ≤ 512 MB
选择文件 → 显示文件名/大小 → 发送 / 取消

[传输中]  1
↑ 一段录音.m4a   发送中 · 1.5 MB / 3.0 MB · 50% · 约 2 秒   [取消]
██████████████████░░░░░░░░░░░░░░

[待接收]  1
▤ 季度周报.pdf   2.3 MB · 来自电脑        [接收] [拒收]

[最近传输]
↑ 旅行照片.zip   12 MB · 电脑已收到 · 3 分钟前
```

1. 选择文件走系统 SAF，不申请存储权限；只拿用户点选的那一个 `content://`。
2. 发送前显示大小与「可执行文件」提示；发送后进入「传输中」，可取消。
3. 断网/失败时行内出现「续传」，使用已保存的 `fileId + sha256` 从服务端记录的位置继续。
4. 「待接收」点「接收」→ 后台下载 → 完成后提示「已保存到 下载/x-hub/xxx」；「拒收」需确认。
5. 「最近传输」展示双方近 30 条，含方向、状态、相对时间。

| 项 | 变更 |

兼容矩阵：

| 组合 | 结果 |
| --- | --- |
| 新 APK + 新扩展 | 全部功能 |
| 旧 APK（≤2.12.4）+ 新扩展 | 待办/笔记同步不受影响；旧 APK 没有文件入口，不发起请求 |
| 新 APK + 旧扩展（≤2.2.3） | 文件接口 404；手机端显示「电脑端需升级到 3.0.0」，同步正常 |

升级注意：

- 升级扩展后，电脑端会在 `.data/files/` 下新建 `inbox/`、`out/`、`tmp/`、`index.json`；不影响 `hub.json`。
- 降级扩展：文件入口消失，已收文件仍留在磁盘，不会删除用户数据。
- 卸载扩展：`.data` 目录默认保留，需要彻底清理时手动删除。

### 9.2 手工

1. 同一 Wi-Fi，手机配对后进入「文件传输」，电脑扩展页同时打开。
2. 手机选一个 300 MB 视频 → 进度到 40% 时关 Wi-Fi → 行内出现「续传」→ 开 Wi-Fi 点续传 → 电脑收件箱出现文件，SHA-256 一致，大小一致。
3. 电脑选一个 200 MB 压缩包 → 手机「待接收」出现 → 接收 → 系统「下载/x-hub/」出现文件，可正常解压。
4. 手机拒收 → 电脑状态变「手机已拒收」；24 小时后未收 → 「已过期」。
5. 电脑「设备」里关闭该手机的文件开关 → 手机刷新后提示无权限；重新打开恢复。
6. 传输 1 GB 过程中观察内存：手机端稳定（按块读写），电脑端 RSS 不超过基线 + 100 MB。
7. 传 `setup.exe`：两端都显示「可执行」红标，且不会自动打开。

### 9.3 性能基线

| 场景 | 文件 | 耗时 | 吞吐 |
| --- | --- | --- | --- |
| 回环（Node 客户端 → 服务，同机） | 32 MiB | **213 ms** | **≈ 150 MB/s** |
| 手机 ↔ 电脑（Wi-Fi） | — | 未做真机基准 | 取决于路由器与信道 |

回环数字说明协议本身不是瓶颈（加解密 + 落盘约 150 MB/s）；真机瓶颈在 Wi-Fi 与手机闪存。未做多块并行，避免把手机 CPU 打满、也避免服务端出现乱序写。

## 10. API 一览

### 手机侧（Bearer）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/files/offer` | `{name,size,mime}` → `{id,chunkSize,chunks,expiresAt,maxFile}` |
| POST | `/api/v1/files/chunk?id=&i=` | 密文块（长度 = 明文 + 16） |
| POST | `/api/v1/files/finish` | `{id,sha256}`，校验后进收件箱 |
| GET | `/api/v1/files/status?id=` | `{state,received,chunks,size}`，断点恢复用 |
| POST | `/api/v1/files/abort` | 取消上传，删 `.part` |
| GET | `/api/v1/files/pending` | 电脑发给本机的待接收列表 |
| GET | `/api/v1/files/pull?id=&i=` | 拉取一块（服务端现场加密） |
| POST | `/api/v1/files/pull/finish` | `{id,sha256}`，确认收到 |
| POST | `/api/v1/files/decline` | 拒收 |
| GET | `/api/v1/files/history` | 近 30 条双向记录 |

### 本机侧（仅 loopback）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/local/files/state` | 收件箱、待发送、配额、设备列表 |
| POST | `/api/local/files/send/init` | 创建发送任务 |
| POST | `/api/local/files/send/chunk?id=` | 裸二进制或 `{off,data(base64)}` |
| POST | `/api/local/files/send/finish` | 生成待接收 |
| POST | `/api/local/files/remove` / `clear` | 删除 / 清空 |
| POST | `/api/local/files/allow` | `{deviceId,allow}` 切换设备文件权限 |

## 11. 已知限制与后续

1. 手机上传时若 App 被系统杀进程，需要回到页面点「续传」；没有做后台 Service 常驻。
2. 电脑端「待接收」只对一台手机有效；拒收即终结，不做多设备广播。
3. 落地文件在电脑上为明文（用户磁盘），未做静态加密。
4. 暂不支持文件夹、多选批量在手机端（SAF 单选）；电脑端支持多选、串行发送。
5. 下一版可做：文件夹打包、传输限速、失败自动重试队列、电脑端「在文件夹中显示」。
